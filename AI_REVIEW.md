## Как строилась работа с AI

Распределение ролей:

**Самостоятельно:** подготовка сервера и Docker; архитектурные решения
(общая внешняя сеть `kuma-net`, `.env` как Dagger Secret, конфиги через
`HOST_PROJECT_DIR`, проверка Grafana по uid, а не по названию); сборка
дашборда в Grafana и его экспорт; запуск и отладка каждого компонента;
chaos-тесты с анализом `docker inspect`/логов; принятие решений, когда
предложение ассистента не подходило под окружение (cAdvisor, restart-policy);
финальный прогон с нуля; README и AI_REVIEW.

**С помощью AI:** черновики compose-файлов, конфигов экспортёров,
Go-кода Dagger-модуля и shell-скриптов; разбор незнакомых ошибок по логам;
быстрая сверка версий образов и API.

Рабочий цикл для каждого этапа:

1. Формулировал задачу с ограничениями (окружение, требования ТЗ, что
   нельзя).
2. Получал черновик, читал его и запускал на стенде.
3. При расхождении с ожиданием возвращал ассистенту: вывод команд, логи, результат PromQL.
   
## Случаи некорректных, устаревших или неоптимальных решений AI

### 1. cAdvisor: устаревший реестр и версия без поддержки containerd image store

**Что предложил AI.** Образ `gcr.io/cadvisor/cadvisor:v0.52.1` со стандартным
набором монтирований — конфигурация, которая годами работала на Docker с
драйвером `overlay2`.

**Как обнаружил.** Target `cadvisor` в Prometheus был `up`, но запрос
`container_memory_working_set_bytes{name="mariadb"}` возвращал пустой результат.
В `docker logs cadvisor` повторялось
`failed to identify the read-write layer ID ... /rootfs/var/lib/docker/image/overlayfs/layerdb/mounts/...`.
Путь `image/overlayfs` (а не `overlay2`) указал на containerd image store,
который включён по умолчанию в новых установках Docker. `docker info` подтвердил
`Storage Driver: overlayfs`.

**Как исправил.** По changelog проекта нашёл, что поддержка
containerd-snapshotter добавлена в cAdvisor 0.54.0 (fix #3643), а образы
переехали в `ghcr.io/google/cadvisor`. Заменил образ на
`ghcr.io/google/cadvisor:v0.60.5` — метрики по контейнерам появились.
Альтернативный путь (отключить containerd image store в `daemon.json`)
описал в README как запасной.

### 2. Утверждение, что `docker kill` запускает restart-policy

**Что предложил AI.** Для chaos-теста ассистент рекомендовал использовать
`docker kill` вместо `docker stop`, утверждая, что после `kill` контейнер
поднимется restart-policy, а после `stop` — нет.

**Как обнаружил.** Первый прогон `chaos.sh --mode=kill` на MariaDB: метрика
`mysql_up` ушла в `0` и не вернулась за 120 секунд.
`docker ps -a` показал `Exited (137)`, а `docker inspect` — `RestartCount=0`:
Docker не перезапускал контейнер. Для Docker `kill`, как и `stop`, является
ручной остановкой, и `unless-stopped` её не отменяет.

**Как исправил.** Ввёл два режима теста: `stop` (по ТЗ, восстановление явным
`docker start` с объяснением в README) и `crash`, где главный процесс
контейнера убивается сигналом с уровня хоста в обход Docker
(`docker run --privileged --pid=host alpine kill -9 <pid>`). В режиме `crash`
`RestartCount` растёт, контейнер поднимается сам — это и есть честная
проверка restart-policy.

### 3. Chaos-скрипт создавал нагрузку, которая искажала сам тест

**Что предложил AI.** В первой версии `chaos.sh` каждый опрос Prometheus
выполнялся через `docker run --rm curlimages/curl ...` — новый контейнер
раз в 5 секунд на протяжении нескольких минут.

**Как обнаружил.** Тест по Uptime Kuma шёл больше 4 минут, VM заметно
тормозила; `docker stats` показывал постоянную активность cAdvisor и
dockerd из-за непрерывного создания/удаления контейнеров. Сама Kuma после
рестарта и так даёт пик CPU (миграции, старт всех мониторов), а тест его
усиливал.

**Как исправил.** Один долгоживущий probe-контейнер на весь тест
(`docker run -d ... sleep 900` + `docker exec`), удаление по `trap EXIT`,
интервал опроса 10 с, сокращённые таймауты. Дополнительно увеличил
`--housekeeping_interval` cAdvisor с 10 до 30 секунд.

### 4. Проверка в `validate.sh` была завязана на захардкоженное название дашборда

**Что предложил AI.** Шаг проверки Grafana искал дашборд через
`/api/search?query=Kuma%20Stand%20Health` — название из примера ассистента.

**Как обнаружил.** `dagger call validate` завершался `RESULT: FAILED` с
`dashboards found: 0`, хотя дашборд был импортирован — он назывался иначе.
Проверка проходила бы только при совпадении с чужим примером.

**Как исправил.** Проверка по `uid` из каждого JSON в
`compose/monitoring/grafana/dashboards/` через `GET /api/dashboards/uid/<uid>`.
Теперь валидация не зависит от названий и автоматически охватывает все
дашборды в репозитории.

### 5. Неверный `.gitignore` для Dagger-модуля

**Что предложил AI.** В стартовом `.gitignore` ассистент исключил `.dagger/`
целиком, а также `internal/` и `dagger.gen.go`.

**Как обнаружил.** После `dagger init` основной код модуля оказался в
`.dagger/main.go` — с таким `.gitignore` он не попал бы в репозиторий, и
решение было бы непроверяемым. Заметил по `git status`, где `.dagger/` не
появлялся среди изменений.

**Как исправил.** Убрал правило; сгенерированные файлы игнорируются
собственным `.dagger/.gitignore`, который создаёт `dagger init`.

### 6. Команда `curl` с фигурными скобками в PromQL

**Что предложил AI.** Проверочную команду вида
`curl 'localhost:9090/api/v1/query?query=container_memory_working_set_bytes{name="mariadb"}'`.

**Как обнаружил.** Команда возвращала `0` даже для существующих метрик:
`curl` трактует `{...}` в URL как glob-шаблон и выбрасывает скобки, запрос
к Prometheus уходит с синтаксической ошибкой, а `jq` на `null` даёт `0`.
Это на время замаскировало реальную проблему с cAdvisor (кейс 1).

**Как исправил.** Передача запроса через `--data-urlencode 'query=...'`
(или флаг `-g`). Так же сделано во всех скриптах репозитория.

## Вывод

AI существенно ускорил работу на этапах, где решение шаблонно (compose,
структура модуля, скрипты, документация). Систематические проблемы —
устаревшие версии и реестры образов, уверенные утверждения о поведении
Docker без проверки, оптимизация по «работает», а не по «работает
правильно на этой машине». Все они обнаруживались одним способом:
прогоном на реальном стенде и чтением логов, а не доверием к тексту.
